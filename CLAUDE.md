# LP Ranger — Project Summary

## Purpose

Auto-rebalancing concentrated liquidity manager for 9mm Pro (Uniswap v3 fork) on PulseChain. **V3 positions only** — V2 positions are rejected with a clear error message. Manages **multiple LP positions simultaneously** across different pools from a single wallet, with per-position start/stop lifecycle (two states: `'running'` and `'stopped'`). All NFT positions for the same pool form a rebalance chain (old positions are drained, not burned). Position token type is **auto-detected**. Supports up to 300 NFT (ERC-721) and ERC-20/PRC-20 LP positions in the browser position store.

## Stack

- **Runtime:** Node.js ≥ 22 (no framework)
- **HTTP server:** Node built-in `http` module (`server.js`) — dashboard + bot auto-start
- **Bot loop:** `src/bot-loop.js` — shared rebalance logic (used by both server.js and bot.js)
- **Bot (headless):** `bot.js` — standalone bot without dashboard UI
- **Dashboard:** `public/index.html` + external CSS (`style.css`, `9mm-pos-mgr.css`, `fonts.css`, generated `ui-tokens.css`) + 88 modular `dashboard-*.js` files bundled by esbuild into `public/dist/bundle.js`
- **Client-side routing:** Navigo (pushState) — bookmarkable URLs like `/:wallet/:contract/:tokenId`
- **Build:** esbuild bundles dashboard JS + ethers.js + navigo from npm, and the User Manual's script on its own; every script and stylesheet a page loads carries the build's `?v=` stamp; fonts self-hosted via `@fontsource` (no CDN dependencies)
- **On-chain:** ethers.js v6.7.1, @uniswap/v3-sdk ~3.28.0 + jsbi (exact ratio math)
- **Concurrency:** async-mutex (rebalance lock for nonce-safe TX serialization across positions)
- **Settings validation:** Ajv, JSON Schema draft 2020-12, strict (every JSON settings file checked against its schema at startup)
- **Formatting:** Prettier, gated by `npm run lint` (which the husky
  pre-commit hook runs)
- **Linter:** ESLint v10 flat config (`eslint.config.js`) + stylelint (`stylelint-config-standard`)
- **Dead code:** knip (devDependency)
- **Tests:** Node built-in `node:test` runner + ganache (in-memory EVM for blockchain mocks)
- **CI:** GitHub Actions (`.github/workflows/ci.yml`) — lint → test (Node 22/24 matrix)

## Architecture Decisions

**V3-only:** The rebalancer supports only V3 NFT positions. `executeRebalance()` refuses, with a clear error, a position with no tokenId or no positive fee tier — what a V2 position looks like.

**Unified entry point:** `npm start` runs `server.js`, which starts the dashboard, resolves the private key, and starts the positions saved as managed (see "Position lifecycle"). Three wallet-unlock modes: (1) the dashboard dialog (default), (2) `node server.js --headless` (terminal prompt), (3) `WALLET_PASSWORD` in `.env` (unattended). With no key and no `--headless`, it runs dashboard-only; `npm run bot` runs without the dashboard.

**Three ways to stop the server.** **`npm run gentle-stop`** (`scripts/gentle-stop.js`), the recommended one and the first every doc names, asks the server to stop once nothing is under way (`POST /api/stop-when-all-clear`, with a CSRF token; `src/stop-when-all-clear.js`). The server holds that stop: from the first request it starts nothing new, and it exits once each rebalance or compound under way, and then each scan still running, has finished, so the scan that follows a rebalance is not cut off. The server decides when, so no check can begin a move between an all-clear and the stop, as one could while gentle-stop asked first and stopped after (the user's design, 2026-10-23: "the bot itself stops itself"). Gentle-stop sends the request again every `shutdown.gentleStopPollMs` (two seconds); a repeat changes nothing, and each answer lists what the stop still waits for, which gentle-stop prints when it changes and once a minute while it does not. An unanswered request is sent again; a refused connection before the server took the stop means no server, and one after means it has closed, so gentle-stop waits for the process to exit. **Ctrl+C and `npm stop` are a force-stop:** the signal handler starts stopping every position and exits within `shutdown.exitTimeoutMs` (three seconds), rebalance or compound under way or not — the operator's choice over waiting (2026-10-17). `npm stop` (alias of `npm run stop`) sends SIGTERM to the PID in `tmp/lp-ranger.pid`, which `src/server-pid.js` writes once the server listens, before the key is resolved and positions start; the signal handlers are installed at the same moment. An `exit` hook removes the file on any exit the process makes itself, `POST /api/stop-when-all-clear` and an uncaught error included; only a kill leaves it, so `npm stop` signals the PID only while it still runs `server.js`. Its lsof-by-port fallback (no file, or a stale PID) likewise signals only this install's `server.js`, never another program on the port.

**What a stop does.** From the moment a stop begins, by signal or by the route, the app is stopping for good (`src/app-phase.js`, never cleared): no position starts, and no bot loop starts a rebalance or compound. Each loop hands its poll `_isStopped`, asked once the rebalance lock is held, so even a poll already under way starts no move. The app's stop counts for a loop whose start is still under way too, since that loop's first poll runs before anything holds the handle that stops it; the position manager records a position before that first poll, so a stop of every position waits for a start under way and then stops its loop. The route's stop (`_handleStopWhenAllClear`, `src/server-routes.js`) waits for each loop's poll, so a move under way finishes before the server exits, rather than being cut off as a signal's three-second exit would (the user's decision, 2026-10-18), and then for each scan still running (its pass, `_scanDone`); Reload Current Position and Re-scan Prices are refused while it waits. It sends the shutdown alert as a signal does.

**Rebalance pipeline:** `src/bot-loop.js` provides the shared bot logic used by both `server.js` and `bot.js`. It polls the pool at `CHECK_INTERVAL_SEC`, checks if the current tick is outside [tickLower, tickUpper], applies the OOR threshold check, checks throttle, then calls `executeRebalance()` which does: getPoolState → removeLiquidity → computeDesiredAmounts → swapIfNeeded → mintPosition. All functions accept injected `signer`, `ethersLib`, and config objects for testability.

**DEX Aggregator swap (primary):** `swapIfNeeded` tries the chain's 0x-v1 aggregator first (`src/rebalancer-aggregator.js`; `chains.json` → `aggregator.url`, chain path included; Watergun on PulseChain) for its low slippage and multi-hop routing, then the V3 SwapRouter; a chain with none uses only the router. **The quote is time-limited** (`aggregator.quoteTimeoutMs`, 15 s): a late one counts as failed, so a hung quote server cannot hold the swap, coins out of the pool, until the connection gives up. `_sendWithRetry` makes up to `maxAttempts` (default 4), handling two failures: (a) **timeout** — not confirmed within `waitMs` of the first submission, so a slow or recovered send gets no extra time → cancel the nonce at the chain's gas multiplier, then re-quote and retry **only once the nonce is settled**; (b) **on-chain revert** (CALL_EXCEPTION, status 0) — the route's pool states went stale and the nonce is spent → no cancel; re-quote at once and retry. **A swap and its cancel share one nonce, so at most one mines, and which one decides what comes next.** `settleNonce` (`src/aggregator-nonce-settle.js`) asks the chain for both receipts rather than trust the cancel's `wait()`, whose null means a timeout, a rejected wait or an RPC error alike; since a reverted swap has a receipt too, the swap's `status` decides. Swap landed (`1`) → it is the result, since this path's only caller falls back to the V3 router on a throw and would swap the balance twice. Swap reverted (`0`) or **cancel** mined → nothing moved and the nonce is spent, so re-quote at the next nonce. **Neither** → the swap can still mine, so `resolveSwapOutcome` (`src/aggregator-nonce-settle.js`) throws with `nonceUnsettled` set and `swapIfNeeded` declines the router fallback. **No cancel failure is raised as an error** (a "nonce too low" refusal, a full txpool that broadcast nothing): an error leaving this module is unflagged, which the fallback reads as "no swap happened", so each goes to the receipt question instead, asked about the refused cancel's hash too (`signedTransactionHash`), since a refusal can follow an earlier copy that went through with its reply lost. "Already known" is no failure: the endpoint holds the swap or cancel, rebuilt from the signed transaction the request carried (`src/held-transaction.js`) and waited on like one just sent. The **swap's own send** is classified, not settled, since a throw there leaves no hash to ask about: `classifyRpcError` says whether the node admitted it, and only `terminal-nonce-unused` — rejected "before it was admitted to the executable pending pool" — may fall back; a transient failure ("may or may not have been broadcast") or a consumed nonce is flagged. The tunables (`url`, `name`, `cancelGasMultiplier`, `waitMs`, `quoteTimeoutMs`, `maxAttempts`) are `config.CHAIN.aggregator`; `url`, `name` and `quoteTimeoutMs` arrive as `config.AGGREGATOR_URL`, `config.AGGREGATOR_NAME` and `config.AGGREGATOR_QUOTE_TIMEOUT_MS`, the last checked at startup by `src/timer-bounds.js`. **A quote naming no price impact is refused** (`quoteImpactPct`, `src/rebalancer-swap-impact.js`), since without a readable `estimatedPriceImpact` the swap cannot be held to the slippage setting; logged with the swap's full context, the refusal counts as a failed quote and sends the swap to the V3 router, safe on a re-quote because the nonce is settled. A full-size swap the aggregator refuses for its impact is tried again in `swapChunkCount` equal parts (bot-config-defaults.json) before the router. The gas limit is `quote.gas` (API-provided, with buffer), per 0x docs; HTTP error responses are parsed for `reason`, `validationErrors` and `issues` (balance/allowance).

**PulseChain gas price patch:** PulseChain supports EIP-1559 but ethers.js v6's `getFeeData()` intermittently returns null/0 for all fee fields, causing TXs with 0 gas price that sit pending forever. `buildProvider()` in `src/bot-provider.js` patches `provider.getFeeData()` at creation time: if the original returns zero/null, it falls back to a raw `eth_gasPrice` RPC call. Both the primary and fallback providers built by `sendTx.init()` go through this patch. This ensures ALL transactions (multicall, swap, mint) automatically get proper gas pricing — no per-call-site overrides needed.

**Unified RPC failover:** `src/send-transaction.js` owns the single active-RPC selection over an **ordered list** of endpoints (`chains.json` → `rpc.urls`; three on mainnet). Reads consult `sendTx.getManagedReadProvider()` — a Proxy that delegates each method call through `sendTx.getCurrentRPC()` and retries failover-eligible errors (`SERVER_ERROR`, `TIMEOUT`, `NETWORK_ERROR`, 5xx) via `sendTx.failoverToNextRPC(failedProvider)`, which **returns whether it actually moved**. **What moves selection is a failure rate, not one error.** `src/rpc-out-of-service.js` is the single decider: every RPC outcome in the process reports to `noteRpcResult` — reads, writes, gas estimates, every attempt the shared retry loop makes, successes as well as failures — and `decideIfCurrentRPCIsOutOfService` answers from the share of failures inside `rpcFailoverRateDurationMinutes` (default 5) against `rpcFailoverRatePercentage` (default 50). Successes count because a rate needs a denominator. Reporting and deciding used to be one act, so a component that fails often and legitimately could only stay silent: `getPoolState` produces up to six failures per call across ten positions, and reporting them would have spent the list. Silence cost more — on 2026-09-29 it logged twenty `g4mm4` failures and reported none, and the endpoint with the best view of the outage contributed nothing to leaving it or to coming back. An HTTP 429 is waited out rather than moved off (`rpcRetryOn429DelaysMs`, `rpcMax429PenaltyMs`, in `_patchRequestPacing`), because it describes our request rate, not the endpoint, and moving carries that rate to the next endpoint. Failover-eligible errors now include the connection-level codes ethers passes through bare — `ECONNREFUSED`, `ENOTFOUND` and the rest, measured, without which a wholly dead endpoint was not failover-eligible at all — and the 4xx answers that describe the endpoint (401, 403, 404, 408, 429); 400 and 413 are excluded because they describe the request. **The caller names the endpoint it saw fail, and selection advances only while it is still on that one.** Selection is process-wide and the bot reads concurrently, so one endpoint's failure arrives several times in the same second; advancing on each arrival spent a three-endpoint list in about that long, and stepping off the end freezes every JSON-RPC request for an hour — on endpoints that were never asked. Naming the endpoint makes the call idempotent: ten failures against the first endpoint advance once, and the other nine return `false`, their callers retrying on whatever the first one moved to. `false` therefore means one of three things — a single-endpoint chain, or the named endpoint is already behind us, or the list is exhausted. Omitting the argument keeps the unconditional step, which is what boot probes want; `null` counts as omitted, so a caller whose provider turned out absent still steps rather than being pinned silently. **The end of the list is a loop, not a dead end:** stepping off the last endpoint holds every JSON-RPC request for `rpcAllEndpointsDownPauseMS` (default one hour, capped at two days, `0` disables), announces it in capitals on Road Sign Yellow, and leaves selection where it is — there is nothing to move to. The pause deadline becomes the sticky deadline, so when the wait is up the ordinary snapback starts the list over at its first endpoint and later failovers walk it in the order they walked it at startup. The loop is what `src/rpc-read-retry.js` depends on: by default it retries until some endpoint serves the read, so an end of the list that did not come round would leave it asking the same dead endpoint indefinitely. **That one loop serves both kinds of caller, because it never decides which endpoint to use** — it asks an injected `current()` and reports to an injected `failover()`, and retries an injected `run(provider)` rather than a provider method, so a composite read keeps all of its parts on one endpoint. Both kinds of caller pass process-wide selection and so follow failover — `getPoolState` included, so it contributes its outcomes to the same rate rather than keeping an endpoint cursor of its own. What it adds is a **bound**: `maxAttempts` sized from `sendTx.endpointCount()` (not `config.RPC_URLS.length`, which `setRpcUrls` can leave disagreeing) times `boundedReadAttemptsPerEndpoint`, with `boundedReadRetryDelayMs` between tries of one endpoint (both in bot-config-defaults.json, shared by pool state and the re-open check's wallet read), and an `onExhausted` raising `PoolStateUnavailableError`, which the dashboard shows as `pool-info-unavailable` and `bot-cycle.js` turns into a `pollError`. Unbounded is only the default, for reads whose answer nobody is waiting on. **A failure is reported only when there is one:** the loop asks `failover` at the top of every attempt, so a caller that has attempted nothing yet — pool state, on its first pass — would otherwise step selection for a read that then succeeds, and step it *unnamed*, which skips the guard that keeps ten concurrent callers from each advancing the list once. **A retry that eventually succeeds logs one line** naming the endpoint that served it and whether that endpoint is the one that had been failing — "recovered, no failover" against "served by X (failed over from Y)". Without it a run of failure lines that simply stopped was indistinguishable from one that gave up, and silence is what an operator reads as a possible outage. Writes walk the same list: `_estimateWithFailover` tries each remaining endpoint in turn but **commits only on success**, so a total outage leaves the bot on its preferred endpoint rather than pinned to whichever it tried last. Boot reachability runs through `sendTx.ensureReachable()`. One sticky window (`rpcFailoverStickyMs` in bot-config-defaults.json, default 1 hour) covers both sides and snaps back to index 0 on expiry; `init({ urls })` is idempotent for a matching list so server.js, bot-loop.js, and position-manager.js can all bootstrap without clobbering state.

**Global RPC request pacing:** every JSON-RPC request in the process — reads, writes, `getBlockNumber`, transaction submission — queues in `src/rpc-request-manager.js` and is released one at a time, one per `globalRPCRequestRateIntervalMS` (default 222 ms, 5 to 2000 so it cannot be turned off, JSON-only setting in `bot-config-defaults.json`). It is a single FIFO queue shared by every provider, because published rate limits are per IP; it is deliberately agnostic to request content, since any exemption is a hole the rate escapes through. Wired in by `buildProvider` (`src/bot-provider.js`), which wraps ethers' `send()`. That is *almost* the one funnel all JSON-RPC traffic passes through, and the exception cost Production an out-of-memory kill on 2026-09-27: **network detection does not use `send()`**. Until a provider is `ready`, `_detectNetwork` reaches past it to the `_send` primitive, and `send()` is itself the only caller of `_start()`, which is what sets `ready`. Held at `acquire()` during a total outage, a provider therefore never becomes ready and every read detects the network over an unpaced, unhaltable path — and since ethers' `call()` starts its `eth_call` *before* awaiting detection, each failure abandons a read already queued behind the halt. So `buildProvider` hands every provider a **`staticNetwork`** built from `chains.json`'s `chainId`: detection then answers from config without touching the wire, which closes the bypass and drops a redundant `eth_chainId` that `getNetwork` had been sending on every single read. The trade is that ethers no longer notices an endpoint changing chain mid-session — a check that only ever compared an endpoint against its own first answer. Pinned by `test/rpc-outage-no-unpaced-detection.test.js`, which needs a real socket because a stub provider has no such seam. A **second** way around the funnel cost Production a corrupted failover decision on 2026-09-30: ethers holds each request's promise for 250 ms and hands the same one back to an identical request inside that window, and **a rejected promise is cached like any other**. The read-retry loop retries with identical arguments, so a failed read was answered from memory rather than from the wire — never reaching `send()`, so never paced, and reported to `src/rpc-out-of-service.js` as a fresh failure on every turn. One refusal by one endpoint was counted 678 times, which made the loop's iteration count, not the endpoint's failure rate, decide the failover; the endpoint itself received one request. `buildProvider` therefore also passes **`cacheTimeout: -1`**, so every attempt is a real request that queues like everything else. The trade is that two identical reads inside 250 ms now cost two requests, which is correct: the queue is what bounds the rate, and a cache that also silently bounded it was answering a question nobody asked it. Pinned by `test/rpc-read-retry-pacing.test.js`, whose sharpest assertion is that retries logged must not exceed requests sent — a retry that never left the process is not a retry. The same queue holds everything when failover exhausts the endpoint list (`halt`, see "Unified RPC failover"), and that hold is absolute for the same reason the pacing is: a rebalance or compound waits it out with everything else, and the request that matters most during an outage is the one least likely to succeed.

**Chunked log queries:** every `eth_getLogs` / `queryFilter` call goes through `src/get-logs-chunked.js`, which splits a block range into windows no wider than `getLogsChunkSize` (default 9,000: 90% of the published 10,000-block limit, which g4mm4 enforces exactly while the other two endpoints accept wider; its range in `setting-bounds.json` stops at 10,000). An endpoint rejects an over-wide query with JSON-RPC `-32602`, which ethers reports as a generic `UNKNOWN_ERROR` with the code nested; `isBlockRangeCapError` detects it by message, and the chunker raises an actionable error naming the span, the cap and the setting to change. Chunk failures propagate by default (`bestEffort` is opt-in per call site), because a swallowed cap rejection reads as "no events", and callers treat an empty result as settled fact, not a gap to retry.

**TX speed-up + auto-cancel:** `_waitOrSpeedUp()` (`src/tx-speedup.js`) wraps the wait of every send through `sendTx.sendTransaction` in four phases. **Phase 1:** wait up to `TX_SPEEDUP_SEC` (default 120 s) from the **first** submission, so a held copy already older is resubmitted at once. **Phase 2:** resend at the same nonce at the higher of current and original gas price, times the chain's `speedUpGasBump` (1.5× on PulseChain). **Phase 3:** wait for either, up to `TX_CANCEL_SEC` (default 3600 s, 60 min in all) and at least `tx.cancelPhaseFloorSec`; if the speed-up could not be sent, the original alone is waited on, so any refusal but "nonce too low" still ends in the cancel. **Phase 4:** a zero-value self-transfer at the stuck nonce, priced by `_cancelGasPrice` at the chain's `cancelGasBump` (twice, on PulseChain) times the higher of network gas and the stuck TX's own, so it outbids it; then wait on every transaction competing for the nonce. If the cancel wins, throw `cancelled: true` and the bot resumes polling; if the move or its speed-up wins, mined before or during the cancel, the move happened and its receipt is the result; anything else at that nonce came from outside the bot, and the move fails naming it. A cancel refused as "nonce too low" may be refused because an earlier copy of it, whose reply was lost, has mined: the refused cancel is rebuilt from the request (`src/held-transaction.js`; signing is deterministic, so its bytes are that copy's) and waited on with the move, so a cancel that went through is still named the cancel. **"Already known" means the endpoint holds the transaction** — the move's, its speed-up or its cancel: `_retrySend` (`src/tx-retry.js`) answers that `evm-rpc-response-codes.json` bucket by rebuilding it from the signed bytes on the error (`src/held-transaction.js`) and waiting on it, never failing the move. **A status-0 receipt is a failure on every road:** ethers' wait throws CALL_EXCEPTION, and `confirmedReceipt` makes the cross-endpoint re-ask and a speed-up's TRANSACTION_REPLACED do the same. **Each phase is the only clock over its interval:** it races the receipt wait against its timer, and the wait's re-ask of other endpoints is bounded only by the phase's **abort signal** (`_phase` passes no deadline). A second, equal bound would race the timer, and a re-ask giving up rethrows the endpoint's error, which phase 1 reads as the move failing — so the bot could abandon a stuck transaction instead of replacing it, exactly when an endpoint had refused all phase. The cancel's wait has no clock (the rebalance lock is held until something mines at the nonce); its re-asks end when the first competitor mines. Coverage is by construction: `send-transaction.js` is the pipeline's only caller, so approve, the removeLiquidity multicall, the V3-router swap, mint, and the compound's collect and increaseLiquidity are all covered. The **aggregator swap** sends through `_retrySend` itself, with its own timeout, cancel and re-quote loop (see "DEX Aggregator swap"), **but shares the receipt wait:** `sendTx.waitForReceipt`, the one way to wait outside `sendTransaction`, is phase 1 alone (`_waitOnePhase`) with the cross-endpoint re-ask **already attached** by `send-transaction.js`, which owns endpoint selection. A bare `tx.wait()` polls only the broadcasting endpoint and cannot follow a failover; its refusal would reach the aggregator's catch, which rethrows what it does not recognise, skipping the cancel and leaving the error unflagged, so `swapIfNeeded` would let the router swap the same balance again. Pinned by a source-shape case in `test/receipt-reask-bound.test.js`, since behavioural tests cannot see a return to a bare wait.

**SDK ratio math:** `computeDesiredAmounts` uses `@uniswap/v3-sdk` exact 160-bit sqrtPrice math (`maxLiquidityForAmounts` + `SqrtPriceMath`) to determine the precise token ratio the Position Manager needs for the target tick range, then computes the swap to convert excess into the deficient token. Falls back to a 50/50 USD value split when no tick range is provided (e.g. price-only callers). The SDK path requires `jsbi` (direct dependency).

**Quote-based swap slippage:** Before executing a swap, the bot simulates it via `staticCall` to get the real expected output (accounting for price impact). The user's slippage % is applied to the *quoted* output, not the spot price — so `amountOutMinimum` is realistic for the pool's actual liquidity. The safety guard aborts the swap when price impact exceeds the user's slippage setting — user must increase slippage and manually rebalance. When a swap abort pauses the bot, it stops retrying until the user changes either Slippage setting (which auto-clears the pause, via `_clearSlippagePause` in `src/server-config-route.js`, keyed on `slippagePctToken0`/`slippagePctToken1` and freeing only the position the save names: another position's pause has its own cause) or triggers a manual rebalance. A rebalance the price outran is held the same way: when the price leaves the new range before the mint (`priceVolatile`, step 6c), with the old position emptied, the bot does not retry on its own (the user's ruling, 2026-10-23) but holds the position at once, with a yellow "Rebalance stopped — the price moved" dialog and the Rebalance Failed Telegram alert, one message for both, advising the owner to weigh any impermanent loss and, if it is acceptable, click Rebalance Now (`src/price-moved-stop.js`); the drained-position retire follows if nothing happens.

**Slippage is two settings, one per token.** `slippagePctToken0` and `slippagePctToken1` are chosen by DESTINATION token — a token0 → token1 swap takes token1's figure, the reverse token0's — since that side is where MEV can extract value. A token with no figure falls back to `slippagePct` in `bot-config-defaults.json` (0.75 as shipped; an operator's copy overrides it, `.env` cannot), a default and **not** a per-position setting. `src/slippage-resolver.js` is the single answer and **every** swap asks it — rebalance (`rebalancer-execute.js`, `rebalancer-correct.js`) and compound (`compounder-swap.js`) alike — so the two Slippage rows show what both moves use. The old single per-position `slippagePct`, left when that row was split, was a third setting that rebalances ignored and compounds honoured. It is in `RETIRED_POSITION_KEYS` and dropped from `bot-config.json` on the next **save** (`_stripRetiredKeys`; nothing reads it meanwhile), with no migration: one number for both sides cannot honestly become two that exist because the sides differ. Except: a strip that would leave a `status: "running"` slot holding only its status is skipped, since `_purgePhantomEntries` deletes that phantom signature on load and the position would silently stop being managed; such a slot keeps the key until a save leaves real content.

**Preserve tick spread:** On rebalance, the bot preserves the existing position's tick spread (tickUpper − tickLower) and re-centers it on the current price via `rangeMath.preserveRange()`. This prevents narrow positions from being widened to match `REBALANCE_OOR_THRESHOLD_PCT`. The range width is determined by the original position, not a config setting.

**Range override toggle:** Bot Settings → **Range** is headed by a "No Override" toggle and a badge reading "Re-Use Existing Position Range" or "Use Settings Below". It gates all three Range settings (`rebalanceRangeWidthPct`, `fullRangeRebalanceEnabled`, `offsetToken0Pct`) and is stored per position as `rangeOverrideEnabled`. With it on, `buildRebalanceOpts` withholds the width and Full-Range and pins the offset to centred (`CENTERED_OFFSET_PCT`, `src/centered-offset.js`: mid-scale, not a default; dependency-free so the dashboard's No Offset button fills the same value), so `_computeRange` lands on `preserveRange()` centred on the current tick. The pin matters: `preserveRange()` keeps the tick spread, but a non-centred `offsetToken0Pct`, saved or an operator's default, would shift where it lands. The toggle is **non-destructive**: it never clears the keys it suppresses (the dashboard greys the fields), so flipping back restores them. `resolveRangeOverrideEnabled` (`src/range-override.js`) alone decides: an explicit boolean wins; otherwise a slot already holding Range settings resolves to `true`, so an upgrade does not silently stop applying them, and an empty slot to the default, `false` as shipped — every position starts on "No Override". `GET /api/status` publishes the **resolved** value, so the dashboard never re-derives the rule. A position with no Full-Range choice saved takes the default (`fullRangeSetting`, same file, an operator's override applied), and the status publishes that for the checkbox too.

**Impermanent Loss Guard (ILG):** A per-position ceiling
(`impermanentLossGuardPct`, default 15) on how far a position may have
fallen before the bot stops rebalancing it. The default is tight because
the two sides are not alike: rebalancing **crystallizes** the loss by
re-minting around the current price, turning a paper loss a recovery
would have undone into a permanent one, while declining costs only fees
the position is largely not earning — it is out of range, which is why a
rebalance was due. Fees are also what would have to earn the loss back,
and in a low-volume pool that can outlast the position. Before every **automatic**
rebalance, `checkIlGuard` (`src/il-guard.js`) compares the hypothetical
post-rebalance position — its LP value, this NFT's compounded fees left
out, slippage excluded — against holding the coins the NFT currently
held was minted with, plus the wallet's coins its compounds took in
since beyond their fees, at today's prices: the Current panel's IL/G
(`snap.totalIL`, with the coins and prices in `snap.ilInputs`), read
rather than recomputed. **The comparison is even** (the user's ruling,
2026-10-23: its purpose "is to compare the existing position in its
state when it was first minted, directly against a hypothetical
rebalanced one. If you add in residual coins, it's not an even
comparison"): it counts no coin in the wallet, neither a rebalance's
leftovers nor a deposit waiting there, so it needs no deposit count
before it measures. **While
price lookups are paused** those figures carry the last prices fetched,
of any age, so once every gate before the Guard has passed they are
worked out again with fresh prices (`snapForGuard`,
`src/bot-cycle-gates.js`): an old price makes the loss look smaller
exactly when a rebalance is due. Rejected
when the projection falls more than the guard percentage below holding.
Not the minted coins' mint-day value, which counted a move both coins'
dollar prices share and which a rebalance does not lock in.
**Read-only and upstream of `executeRebalance`:** both inputs come
from the poll cycle's figures, and the gate sits in
`_checkRebalanceGates`, so a rejection cannot reach `removeLiquidity` —
the position is left exactly as found. A rejection is **not** a
rebalance: `throttle.recordRebalance()` and `_recordPoolRebalance()`
live in `_handleRebalanceSuccess`, which is never reached, so the daily
cap and doubling window are untouched. Skipped for user-forced
`Rebalance Now`, like every other gate. A Rebalance Now never meets a
running scan: the server refuses one while a scan is running on its
position, its dialog waiting for the scan to end, and no scan starts
while one waits to be made (`src/scan-state.js`). Skipped too while the
position holds no liquidity (`isThisPositionDrained`,
`src/position-drained.js`, the user's decision, 2026-10-23), as after a
rebalance that emptied the old position and failed to mint: the bot
retries the mint as an automatic rebalance, the drain has locked the loss
in, and the Guard, counting no coin in the wallet, would read the empty
position as a total loss and leave the coins idle. Fails open when the baseline has
not resolved yet. Retries back off 4 h → doubling → 1 week
(`ilGuardRetry` group), with the `ilGuardRejected` Telegram alert riding
the same timestamp; saving a position's Guard lifts its wait
(`clearIlGuardWait`), so the next poll reads the new value, and a successful rebalance ends the block,
wait and alert both (`endIlGuardBlock`), since the new NFT is measured against its own minted coins. Full detail in docs/engineering.md §
"Impermanent Loss Guard".

**Tick containment:** `computeNewRange` includes a post-rounding check that ensures `lowerTick < currentTick < upperTick`. When coarse tick spacing (e.g. 50 for fee tier 10000) causes both rounded ticks to land on the same side of the current tick, the range is shifted to contain it. This prevents minting out-of-range positions that accept only one token.

**OOR threshold:** `REBALANCE_OOR_THRESHOLD_PCT` (default 5) is how far the price must move **beyond** the position's boundary before the price-distance trigger fires, as a percentage of the **position's price-range width**, NOT of the boundary price (`_isBeyondThreshold`, bot-cycle-triggers.js: `price < lower − (upper − lower) × pct` or `price > upper + (upper − lower) × pct`). Its range in `setting-bounds.json` starts at 1, so it cannot be 0. The threshold and the OOR timeout are independent triggers; either alone fires (`beyondThreshold || timeoutExpired`). Out of range but inside the threshold zone, the dashboard shows an amber "WITHIN THRESHOLD" banner.

**OOR timeout:** `REBALANCE_TIMEOUT_MIN` (default 180, i.e. 3 hours) triggers a rebalance after the position has been continuously OOR for the configured duration, even if the price hasn't crossed the OOR threshold bars. The bot tracks `oorSince` (timestamp of first OOR detection). When the timeout expires, the rebalance falls through to the existing throttle + execution path — no special bypass. `oorSince` is cleared when the price returns to range or after a successful rebalance. Set to 0 to disable. The dashboard shows a countdown ("Timeout: MM:SS") in the "WITHIN THRESHOLD" banner. The setting has its own Save button and is persisted to `bot-config.json`.

**USD pricing:** current prices are asked of Moralis (when a key is stored and enabled), then GeckoTerminal, then DexScreener, each only where the chain's `priceServices` names it (`src/price-sources-current.js`); each service's base url is in `price-services.json`, read through `src/price-service-urls.js`. Cached in memory for `priceCacheTtlMs` (two minutes as shipped). See `src/price-fetcher.js`. Historical prices fetched from GeckoTerminal OHLCV API (free, no key, 30 calls/min). USD values (token prices, exit/entry amounts) are recorded in `rebalance_log.json` at rebalance time to avoid needing historical price lookups.

**Multi-position management:** The tool manages **multiple LP positions simultaneously** across different pools from a single wallet. Each managed position gets its own independent `startBotLoop()` instance sharing a single provider/signer. A **rebalance lock** (`src/rebalance-lock.js`, backed by `async-mutex`) ensures only one position sends transactions at a time (same wallet = same nonce), while all positions continue polling independently. The `src/position-manager.js` orchestrator tracks all managed positions with start/stop lifecycle (two states: `'running'` and `'stopped'`). When rebalancing, the old NFT is drained (`decreaseLiquidity` + `collect`) but NOT burned. Rebalance history is detected via consecutive mint events. Closed positions (liquidity=0) are displayed but the bot skips rebalance checks.

**Position key format:** All per-position state is keyed by a **composite key**: `blockchain-wallet-contract-tokenId` (dash-separated). Example: `pulsechain-0x1111111111111111111111111111111111111111-0xCC05bf158202b4F461Ede8843d76dcd7Bbad07f2-157149`. Built by `compositeKey()` (`src/bot-config-v2.js`) and parsed by `parseCompositeKey()` (`src/composite-key.js`, dependency-free so the offline `util/` tools share the rule without loading the app's config). The same components appear in the URL path.

**Position lifecycle:** `POST /api/position/manage { tokenId }` starts a new bot loop. `DELETE /api/position/manage { key }` stops and removes from management (sets `status: 'stopped'`, keeps config data for history). No pause/resume — only start and stop. Focus is client-side (URL determines which position a browser tab shows) — the server does NOT track focus. The `handleManage` start path uses a `_starting` Set guard + try/catch/finally to prevent duplicate bot loops and ensure cleanup on failure.

**The next launch's list:** the positions saved as `status: 'running'`. Manage adds to it, Stop Managing and a retire remove from it, and no stop of the app, gentle or not, changes it.

**The start-up** (`src/server-auto-start.js`, which the server and the headless `bot.js` share) runs once the wallet unlocks, over the listed positions of this chain and wallet; one of another wallet or chain waits for that launch. With no wallet loaded (a dry run without a key, or a key in `.env` with none imported), it takes every wallet's listed positions on this chain, checks no owner, and keys each pool by the position's own wallet, as a Manage does. First it reads each listed position's owner and pool, and takes off the list each one that cannot be managed: its NFT left the wallet or no longer exists (the contract reverts when asked its owner), or another listed position keeps its pool. LP Ranger manages one active position per pool, so each pool keeps its open position, else the first listed (`poolHoldersForStartUp`, `src/pool-already-managed.js`), with no fallback if that one fails to start. One whose owner or pool could not be read stays on the list unstarted, since an unread pool cannot be shown free; a Manage whose pool cannot be read is refused the same way (503 `pool-info-unavailable`). Then it starts the rest one at a time across a poll interval; one that fails to start stays on the list for the next launch. While it runs, `GET /api/status` reports its progress (`startingManagedPositions`), and the dashboard's badge reads Syncing for every position, which keeps Manage and Stop Managing disabled. The server refuses a Manage or a wallet import with 409, since each would start positions, and a second start-up does nothing. A Stop Managing still goes through, since it starts nothing: the start-up reads each saved status again at the position's turn.

**Rebalance lock:** No timeout-based release — blockchains can hold a TX pending indefinitely. If stuck, the lock holder speed-ups (1.5× gas) then sends a zero-value self-cancel at the stuck nonce. Lock only releases after TX confirmation. This guarantees the nonce is always clear before the next position rebalances.

**Throttling:** Per-position throttle (independent doubling mode per pool) and a **per-pool daily cap** (default 5): each pool's daily count is tracked independently in `position-manager.js` (`_poolDailyCounts`, restart-safe via rebalance-log seeding) against the same `Max Rebalances / Day` value, so a volatile pool hitting its cap doesn't block other pools. **Every successful rebalance counts toward the cap** — automatic OOR, OOR-timeout, and residual-cleanup rebalances are all gated by it AND increment it; manual (user-forced) rebalances bypass the gate but still increment the count (`bot-cycle.js` `_checkRebalanceGates` + `_handleRebalanceSuccess`). A volatile pool's doubling doesn't slow a stable pool.

**Compounding:** `src/compounder.js` collects unclaimed fees via `pm.collect()` and re-deposits them via `pm.increaseLiquidity()` on the same NFT — swapping only to bring them to the range's ratio (`src/compounder-swap.js`), with no range change and no new NFT. Mission Control offers "Compound Now" (disabled when fees < `COMPOUND_MIN_FEE_USD`, default $1) and auto-compound (toggle + USD threshold, default $5), which checks every in-range poll, spaced `max(compound.autoSpacingPolls × CHECK_INTERVAL_SEC, compound.autoSpacingFloorSec)` apart (app-runtime.json; 5 polls and 300 s as shipped, ranges in setting-bounds.json). Neither starts while a scan runs on the position: the server refuses a Compound Now then, and its dialog waits for the scan to end, since the scan's rebuild of the compound list would leave the compound out of Fees Compounded (`src/scan-state.js`). Compounds are tracked as **coins**: `compoundedAmount0` / `compoundedAmount1` per position and `nftCompoundedAmountsByTokenId` per NFT in the chain (both records, in `app-data/position-records.json`). **A compound counts only the fees its deposit put back.** When its ratio swap runs, the deposit is offered the wallet's whole balance, so it can take in a deposit the owner made or coins a rebalance left; none is a fee: counted as one, it would raise Fees Compounded by its size and read in the Lifetime IL/G as a loss of that size. The compound reads the wallet before its collect and just before its deposit, and keeps the fees on its record (`amount0Compounded`, `amount1Compounded`, `src/compounded-coins.js`), which the running total, the per-NFT coins read back from the chain, the rebuilt list and the unmanaged view all count; a compound without them counts its whole deposit. Its deposit takes only what fits the range, so some fees can stay in the wallet: its record keeps them too (`amount0FeesLeft`, `amount1FeesLeft`: its fee coins after the swap, from its own transactions, less the fees put back; none when those could not be read), and the Current panel shows them on its Fees Left Over line, which Profit adds (`feesLeftInWallet`; `currentFeesLeftUsd` from the bot and from the unmanaged view's saved list). The Current IL/G and Net P&L do not count them. A deposit the owner sends while the compound runs lands between those readings, where they cannot tell it from fees, so two figures come from the compound's own transactions: what the collect brought in is its `Collect` event's amount, capped at the wallet's rise (`src/compound-collect.js`), and the fees are capped at the fee coins as the collect and the swap moved them, the swap's exchange read from its receipt (`exchange`, `src/rebalancer-swap-balance.js`). The Lifetime scan counts no compound this install made as money put in. No USD total is persisted: a saved dollar figure is true only at the price that computed it, and its error grows with the position's age. Every current total is the saved coins times the current price where shown: `snap.totalCompoundedUsd` on every poll in `overridePnlWithRealValues`, with `src/coin-value.js` the one place that multiplication lives. The deliberate exceptions are historical: Total Lifetime Deposit values each deposit at its own block, the HODL Baseline's Entry Value stands at the NFT's mint, and the Historical P&L table's closed epochs keep the dollars they closed at. Lifetime fee earnings = `currentFeesUsd` (live unclaimed) + `snap.totalCompoundedUsd` (swept into liquidity), with no subtraction term; the old per-epoch `totalFees` aggregate, which double-counted, is gone. Historical compounds come from each chain NFT's `IncreaseLiquidity` events (first = mint deposit, later = compounds); the lifetime total is each NFT's `Collect` amounts less the principal its `DecreaseLiquidity` events released (`lifetimeFeeAmounts`). Config writes are atomic (see "Atomic config write").

**Atomic config write:** `saveConfig` writes to `app-config/user-configurable/bot-config.json.tmp` first, then atomically renames to `app-config/user-configurable/bot-config.json`. Prevents empty-file corruption if the process exits mid-write (SIGINT race during shutdown).

**App-managed config layout:** All runtime state files and static tunables live under `app-config/`. See the `app-config/` section of `server.js`'s file-header JSDoc for the full layout, file inventory, migration behavior, and the rules for where future config files should go.

**Post-rebalance key migration:** When a position rebalances and mints a new NFT, the composite key changes (new tokenId). `position-manager.migrateKey()` and `bot-config-v2.migratePositionKey()` carry over HODL baseline and residuals from the old key to the new key. P&L epochs do NOT need migration — they're keyed by pool identity, not tokenId (see epoch cache below).

**P&L breakdown:** Two components: (a) price-change P&L (position value change from token price movements, including IL), and (b) fee P&L (trading fees earned while in range). Per-day aggregation, newest first; only days with activity get a row (empty days are omitted, not padded). Historical USD token prices stored per-epoch for accurate retrospective P&L.

**Gas tracking:** An NFT's gas is stored as **coins** and priced where shown, like compounded amounts. `receiptGasWei` (`src/receipt-gas.js`), the receipt-side counterpart to `coin-value.js`, is the one place `gasUsed × gasPrice` lives, and returns only wei, so no dollar conversion can hide beside it. An NFT's whole gas (its mint TX plus every charge against it) is summed in wei by `position-history._supplementGasFromChain` into `nftGasWeiByTokenId`. No period gets a copy of it: **the Current panel** prices that NFT's wei at today's price (`_weiToUsd`, `bot-pnl-current-nft.js`), and **a closed period** in the Per-Day table at its own close day (`epoch-reconstructor._gasSpentAt` → `pastGasCostUsd`), so those rows each imply a different historical rate; where that day has no native price, or is not recorded, the row's Gas, Profit and Net P&L show a dash, never a figure at today's price. Two charges nothing re-derives are persisted at once, in dollars at that day's price beside the coins. **Compound gas** goes onto the OPEN period (`bot-cycle-compound.js`). **A failed rebalance's or compound's gas** goes into the position's records instead, with when it was paid (`failedMoveGas`, `recordSpentGas`, `src/spent-gas.js`, from `bot-cycle.js` and `bot-cycle-compound.js`), and is never added to a period: the periods live in the epoch cache, which Reload Current Position and a cleared scan cache rebuild from the chain, and the chain does not show this gas. `snapshot(price, charges)` (`src/pnl-tracker.js`) adds each charge to the lifetime gas and to the Per-Day row of the period it was paid in, every poll, so a rebuilt period has its charges back and none is counted twice (the user's approval, 2026-10-19). The charge is whatever the failed move's error carries as `gasCostWei`, cancelled or not: a stuck transaction's cancel, or a failed swap attempt's approvals, reverted swaps and cancels. **A swap's figure counts the routes it gave up on:** a failed attempt puts what it paid in its error's `gasCostWei`, each layer adding only its own (the aggregator's retry loop its reverted swaps and cancels, the aggregator its approvals, the chunked swap its earlier chunks), and `swapIfNeeded` adds that to the route that ends the swap, or to the final error. **A failed rebalance or compound also carries every earlier step that confirmed** — the V3 router's approval, the mint's and the deposit's approvals, corrective-swap rounds, the drain before a failed swap or mint, the collect before a failed deposit (`carryingGas`, `addSpentGas`) — and `sendTx.sendTransaction` puts a reverted transaction's own gas on its CALL_EXCEPTION. A rebalance stopped for price volatility and a compound that collected no fees record what they paid too. Compound gas from before the open period is held apart in `importedGas`, so the lifetime total counts it and no Per-Day row does. A speed-up replaces at the same nonce, so the confirmed receipt already shows the gas actually paid.

**Disk cache:** `src/cache-store.js` provides JSON file-based caching with TTL for expensive blockchain queries (event scanner 5-year lookback, P&L history). Cache filenames are scoped by `blockchain-contract-wallet-pool` to isolate data across chains, contracts, and wallets. Every scan cache lives in `app-data/scan-cache/` (`src/scan-cache-dir.js`), which an update carries forward: each can be rebuilt from the blockchain if deleted, but that takes about an hour per position, so none is in the disposable `tmp/`. Under `node --test` the folder is the test process's own, so no test touches the operator's caches. After a successful rebalance the bot sets `_needsFullRescan` (`src/bot-recorder.js`) and triggers the scan immediately (`src/bot-cycle.js`), which runs the event and lifetime scans together so the new NFT mint event is picked up. A scan never runs beside a move of its position (`src/scan-state.js`). No scan starts until every move of the position is cleared (`isItOkayToStartAscan`): none while a poll decides a rebalance or compound, allowed or not (`duringMoveInitiation`), and none while a Rebalance Now or Compound Now waits to be made, however long, so a scan asked for then, the rebalance's own included, waits and starts when the poll that clears the move ends. Over the same window a coin move is under way (`isAcoinMoveUnderWayOnThisPosition`), and the server refuses Reload Current Position and Re-scan Prices with 409 `coin-move-under-way`: a move counts from its first gate, before it holds the rebalance lock and raises `rebalanceInProgress` or `compoundInProgress`. Scans held back resolve to one, since each is the same whole operation. And no move starts while a scan runs (`isAscanRunningOnThisPosition`): the server refuses a Rebalance Now, a Compound Now and a re-open retry, and the bot makes no automatic rebalance or compound, so none can clear another's rescan request; the `lifetimeRescanTimer` in `src/bot-loop.js` (every `poll.lifetimeRescanCheckMs` in app-runtime.json) is the retry for a scan that does not finish. The request lives in memory, so a start also recounts the deposits whenever the count stops short of the current NFT's mint (`depositsBehind`, `lifetimeScanPlan`), and a stop that cuts that scan off loses nothing. That scan also re-derives the lifetime HODL, because the rebalance minted with the wallet's whole balance — so coins that arrived since the previous mint are deposits in the new NFT and count toward Total Lifetime Deposit. The event cache itself is **not** invalidated on rebalance — `clearPoolCache` runs only from the Reload Current Position handler (`src/server-reload-position.js`). Browser caches rebalance events in localStorage (`9mm_rebalance_events`) for instant display on page load; this localStorage cache is cleared on position switch via `resetHistoryFlag()`.

**Event scanner rate limiting:** the scanner no longer paces itself — every request is spaced by the global queue (see "Global RPC request pacing"), which is the only level that can bound a rate, since each chunk fires two queries in parallel. With 9,000-block chunks, a 5-year scan (~15.8M blocks) is ~1,750 chunks / ~3,500 requests. Pool-age optimisation reduces this for younger pools, and the pool-creation finder scans newest-first with an early exit so a recently created pool resolves in a handful of windows rather than grinding up from genesis.

**Per-NFT scan windows:** the `IncreaseLiquidity`/`Collect`/`DecreaseLiquidity` history behind compound detection, HODL baselines and lifetime P&L runs once per NFT in a position's rebalance chain, so a long chain multiplies whatever the per-NFT window costs. Every such scan is **floored** at the NFT's own mint block, taken from the rebalance events the caller already holds (`newTokenId` + `blockNumber`) — no extra RPC. **There is no upper bound; every scan runs to the chain head.** One could only come from the app's inferred succession, and `pairTransfers` reads consecutive mints as successive rebalances — sound only when every mint in the pool IS a rebalance. A dust mint from a failed or partial rebalance is indistinguishable in the Transfer log, so the NFT it appears to replace can still be funded and drain later; bounding there truncates the scan, and the loss is silent both ways it lands (zero Collects → epoch skipped as "incomplete data"; a mid-life compound's Collect → read as the exit value). `src/nft-mint-blocks.js` owns the floor rule (`mintBlocksByTokenId`, `nftScanFrom`, `nftScanFromBlock`, `chainScanFloor`) and deliberately exports no upper-bound helper. Two rules decide correctness: a repeated id resolves to the EARLIEST block (a floor above an NFT's first event drops those events and the caller reads the short result as "never fired"); and `nftScanFrom` combines with `Math.max`, so a mint block tightens the pool's floor and no scan starts below that floor. The chain's oldest NFT has no mint block in the events (it appears only as an `oldTokenId`) so it falls back to `chainScanFloor`, which lifts the pool's creation block to `events.firstMintBlockNumber`. On a 132-rebalance chain in a pool two years older than the first deposit: 954 chunks per NFT for the pool's window, 168 with the mint floor. Every whole-chain read is **one batched pass** (`scanChainNftEvents`, `src/nft-events-batch.js`), and a scan pass reads the chain **once**: the bot's lifetime scan (`fetchAllNftEvents`, prepared by `prepareLifetimeRead`), epoch reconstruction (Collect and DecreaseLiquidity only, read before any epoch is built — taken from the lifetime read when that read runs in the same pass, otherwise `scanChainCollectAndDrain`), The unmanaged details view makes no such read at all: it shows no Lifetime panel and no Per-Day P&L, so it has nothing to walk a chain for — its Current-panel Fees Compounded and Gas come from a single-NFT scan floored at that NFT's own mint. The lifetime scan reuses the pass's read only while `chainSignature` still matches, since a manual rebalance can land mid-pass; `test/bot-recorder-lifetime-share.test.js` pins that every lifetime read starts from the pool's floor, which is what lets reconstruction take whole histories from it. `tokenId` is the first indexed parameter on all three events and a topic slot OR-matches an array, so one filter carries every NFT; logs are partitioned by `topics[1]`, re-floored to each NFT's own window, and sorted into chain order, and every requested id gets an entry (`eventsFor` throws for one that was not requested). A reader names the event types it needs, and an entry carries only those. A 133-NFT chain reads in minutes rather than hours. `test/nft-scan-floor-coverage.test.js` fails CI for a scan that ships without a floor, matching on helper name — the batch entry points included — and on the shape of a chunked scan whose label names a tokenId, and requires each chain reader to hand the batch the chain's mint blocks. Full detail in docs/engineering.md § "Per-NFT Scan Windows".

**Dashboard defers to the bot on managed positions:** the dashboard's unmanaged-details path computes the same per-NFT history the bot computes for a managed position, so running both is two full passes over every NFT. `shouldSkipUnmanagedFetch()` (`public/dashboard-unmanaged.js`), consulted from `flushPendingUnmanagedFetch()`, suppresses the fetch only when a poll HAS landed and the position is managed. `hasPolled` is required because `isPositionManaged()` reads a Set that is restored from localStorage on load for instant badge render, so before a response arrives it may be a carry-over from a session in which the position was still managed; suppressing on it would leave a genuinely unmanaged position with nothing to populate its KPIs. After the first response the value is authoritative — the server's `managedPositions` is the union of live bot loops AND positions whose saved status is `running` but have not started yet, which matters because the bot starts positions on a stagger and the flush fires at wallet unlock.

**Dashboard values are checked on the server, not in the browser:** `src/config-bounds.js` alone decides whether a typed value may be saved: every setting the dashboard sets, plus the price-cache settings `POST /api/config` takes without a dashboard field; a test fails any accepted key without a check. Each setting's rule is a JSON Schema (`settingSchemas`), and the startup check builds bot-config.json's schema from the same ones, so a value a save refuses stops startup too. The route takes no record: the bot's own records (HODL baseline, residuals, compound history and tallies, per-NFT gas, lifetime deposit) are held to the shape the bot writes (`src/config-record-checks.js`, with the kinds the shipped-values test uses, `src/value-kinds.js`) when the startup check reads the records file. `POST /api/config` (`src/server-config-route.js`) asks it before applying anything, so a refusal leaves no trace (nothing assigned, no provider rebuilt, no paused loop freed) and answers 400 with `invalidValueForKey` naming the setting; a missing, malformed or other-chain position key is refused there too, as a malformed request without that field. **Refused, never corrected**, since a value quietly moved to the nearest allowed figure runs the bot on a setting nobody chose: on that 400 the page's one save path (`public/dashboard-config-save.js`) empties the field, asks the server about the position on screen and fills the field from that answer, as when the position came on screen, and says why; it keeps no accepted value of its own, since one kept by field could be another position's (the user's design, 2026-10-19). **Every range is in `setting-bounds.json`**, at the setting's own path, read through `src/setting-bounds.js` and judged by `withinBound` (`src/range-check.js`, dependency-free so the dashboard shares it) for this module, the timer rule, `src/config.js` (no startup with any of the five Bot Settings `.env` can set out of range; `parseBoundedSetting`, `src/runtime-flags.js`) and the shipped-defaults reader (`src/bot-config-defaults.js`: an override out of range stops startup with one message naming each setting, range and value, group members and list entries included; a later read keeps the shipped default; no fraction is rounded). Only the shipped copy is read, since a range an override could widen would bound nothing. The help gets ranges and defaults from the server (`GET /api/help-figures`, `src/resolved-settings.js`), so it quotes what this install enforces and runs on, overrides and `.env` included. No setting the dashboard saves becomes a `setTimeout` delay; where one is read, `src/timer-bounds.js` rules. `rpcUrls` must pass `validator.isURL` (http/https, protocol required, `require_tld` off so a node on the operator's machine passes). Two values are not refusals: **`null` clears a setting** (the key is deleted and the shipped default stands), which is why an empty field is sent as `null`; and **zero is a real setting** for several keys — a price override of 0 means "no override", an OOR timeout of 0 "off". The browser keeps only what is not validation: the two slippage confirmations, warning of an accepted but expensive value at the tiers the server sends (`ui-defaults_non-layout_for-server-up-scenario.json`).

**Every setting is checked before the app starts:** `server.js` and `bot.js` call `refuseToStartOnBadSettings` (`src/settings-check.js`) before they read a setting, and it lists every problem at once and exits: the JSON settings files with the operator's copies over them, each against its JSON Schema (`src/settings-file-rules.js`, Ajv, draft 2020-12, strict; every group names the keys it takes and refuses any other, so a setting in a file that does not read it is refused; the shipped-values test holds the shipped files to the same schemas), `.env` (`src/env-settings.js`), `bot-config.json` against a JSON Schema built from each setting's schema a save is held to, with the same strictness (`src/bot-config-checks.js`), and the records file beside it, against the shapes the bot writes. A problem is a value of the wrong kind or outside its range, a setting LP Ranger does not read, a file that is not valid JSON, or a copy of a file the app never reads from `user-configurable/`; a retired key is left for the next save to drop. Every `.env` variable is read through `readEnv`, by the same rule: on/off is exactly `true` or `false`, a number plain digits, nothing coerced. `npm stop` and `gentle-stop` skip the check and read no setting but the shutdown timings and where the server listens (`src/server-address.js`; `npm stop` reads the port only when the PID file fails it), so a bad setting elsewhere never keeps an operator from stopping a running server. The `validate-config-values-with-any-user-overrides` diagnostic (`util/diagnostic/`) gives the same verdict without starting. The test suite checks only what ships (the JSON defaults and `.env.example`), so local and CI results agree.

**Bot config persistence (v2):** `bot-config.json` (`src/bot-config-v2.js`) has two sections: `global` (RPC list, Moralis on/off, approval multiple, gas fee limit, price-cache settings) and `positions` (per composite key: status, threshold, timeout, slippage and the rest of the position's settings). `positions` is the **single source of truth**: managed positions are `managedKeys(cfg)`, the keys whose `status === 'running'`, with no separate `managedPositions` array to fall out of sync. **The bot's records for each position are kept apart**, in `app-data/position-records.json` (`src/position-records.js`): the HODL baseline, compound history and coins, gas per NFT, lifetime deposit, residuals, when it last compounded, and the gas each failed move paid (`RECORD_POSITION_KEYS`, `src/bot-config-keys.js`). In memory a position's slot holds both: `loadConfig` merges the records in before its phantom purge, since a managed slot can hold its status alone when everything else is a record, and `saveConfig` writes each key to its own file. Resetting the settings therefore leaves the figures, and `POST /api/config` takes settings only (`SETTING_POSITION_KEYS`). A release that kept records in bot-config.json is moved by `node ./util/migration`; until then the startup check names each record left there. P&L epochs live in the epoch cache (see below), not here. `POST /api/config` **requires** a fully-qualified `positionKey` (checked by `parseCompositeKey`) with any position-specific key and answers 400 without one; global keys (`GLOBAL_KEYS`) need none.

**Pool-age optimisation:** the event scanner resolves the block a pool was deployed in and skips everything before it, saving thousands of RPC queries for pools younger than 5 years. `src/pool-creation-finder.js` binary-searches `eth_getCode` — contract code is account state and state is addressable per block, so the lowest block holding code is the deployment block: 27 calls over a 27.5M-block chain, versus the 900–1,100 chunked queries a Factory `PoolCreated` log scan needs (those events are ordered by block, not by pool address, so they cannot be bisected). The search needs historical state; a pruned node errors rather than answering empty, so it cannot return a wrong block — the error reaches `getPoolCreationBlockCached`, which returns `0`, and the caller keeps its own floor. Cached permanently in `app-data/scan-cache/pool-creation-blocks-cache.json`.

**Activity Log figures:** each Rebalance and Compound entry shows, under its date, one figure twice as a percent, a Rebalance's whole and a Compound's to three decimal places: **Historical**, stored with the entry's record the moment the move succeeds and never worked out again, and **Current**, the same figure at today's prices, worked out in the browser from the record's coins (`src/coin-value.js`, bundled, so both use one formula). A Rebalance's figure is the impermanent loss or gain its swaps left, from the wallet's three readings (`walletReadings`: before the drain, after it, before the mint), with a deposit still waiting in the wallet set aside by its share of the value: the Lifetime accounting's deposits for the mint (`lifetimeHodlAmounts.deposits`, `src/lifetime-hodl.js`), those the deposit count recorded after the old NFT's mint and the scan's own entry at the mint tagged `fresh`, capped at the wallet before the drain. Historical needs no deposit and is stored at once; the coin figures (`beforeRebalance`, `afterRebalance`) wait, marked `figuresDue`, for the scan pass that counts the deposit (`src/bot-rebalance-figures.js`), and live on the event-cache record. A Compound's figure is the fees it collected (`feesCollected`) as a share of the position after it, from the liquidity it added (`src/compound-activity-figures.js`). A rebuild of the compound list works the figure out from the chain and keeps each live entry's trigger (Auto or Manual) and figures, matched by transaction, so Reload Current Position and the scan-cache clear leave `compoundHistory` for it to replace. A figure or amount a rebuild cannot price keeps the one the entry held (`_chainOrEarlier`, `_amountOf`), and the rebuild's prices carry the operator's price overrides. A figure stored as a dash for want of a price is worked out again: a Compound's by every rebuild of the compound list (Re-scan Prices and Reload Current Position), a Rebalance's when Reload Current Position reads its event again (`_withFigure`). A Compound entry's $usd amount is marked "(historical $usd)" while its record carries the prices of the compound's own time (`price0`, `price1`, which only the bot's live record keeps); a rebuild writes every amount at its own prices, without them. An entry from before the figures shows "Old Log: Unavailable". When a scan of the position on screen has finished, the log takes that position's Rebalance and Compound entries off (`removePositionActivityEntries`, by `poolKey`) and the history pass draws them again from the records the scan left. Re-scan Prices is one such scan: it rebuilds the compound list, working out from the chain the figures of each compound that had none. A managed position's entries wait for its second data load, the status answer that brings its pool key once the server has read the position from the blockchain (`canDrawPositionEntries`), from the live check and the history pass alike, so each is drawn with its position line and filed under its pool. A Rebalance entry names what started it (`trigger`, kept on the event-cache record and taken back from the rebalance log when a rebuild finishes the event), in one wording for the live check and the history pass (`public/dashboard-rebalance-log.js`). The dashboard keys the entries it shows by kind and transaction, so none is drawn twice. Full detail in docs/engineering.md § "Activity Log Figures".

**Lifetime P&L:** User-entered "Initial deposit" (USD) is persisted to both localStorage and server `bot-config.json`. Lifetime P&L = currentValue + fees + realized − initialDeposit. If no user-entered value, falls back to bot-detected entry value. "Realized gains" is also user-entered for coins sold out of the LP.

**Impermanent loss/gain:** All IL/G math is consolidated in `src/il-calculator.js` — single source of truth, no duplication. Four exported functions: `calcIlMultiplier(priceRatio)` (v2 formula), `estimateLiveValue(entryValue, priceRatio)` (v3 estimate), `computeHodlIL({ lpValue, hodlAmount0, hodlAmount1, currentPrice0, currentPrice1, residualValueUsd })` (HODL comparison using actual deposited token amounts), and `hodlValueUsd` (its HODL side alone, which the Impermanent Loss Guard measures against). The HODL comparison uses **only current prices** for valuation — the original deposited token amounts (from the `IncreaseLiquidity` event on the mint TX) determine the HODL portfolio. No historical USD prices are needed for IL. The lifetime figure is `IL = (LP_value − compoundedFees + currentResidualValueUsd) − (amount0_deposited × currentPrice0 + amount1_deposited × currentPrice1)`, the deposited amounts including what the owner deposited to the wallet since (see "Deposit count"): the residual credit counts those coins, so holding must too. **The current figure counts no coin in the wallet** (the user's ruling on the Impermanent Loss Guard, 2026-10-23: the comparison must be even, the position as minted against the same position rebalanced): `IL = (LP_value − this NFT's compoundedFees) − (minted coins + the wallet's coins its compounds took in since, beyond their fees) at current prices`, those coins from the compound records (`walletCoinsPutIn`, `src/compounded-coins.js`), so a deposit or a rebalance's leftovers waiting in the wallet move it only once a compound takes them into the NFT. Compounded fees are removed from the LP side because compounding calls `increaseLiquidity`, so they are part of the liquidity `positionValueUsd` measures while the HODL side stays fixed at the deposited amounts — leaving them in would report reinvested earnings as LP outperformance, and Profit already counts them. `snap.lifetimeIL` removes `snap.totalCompoundedUsd`; `snap.totalIL` removes only this NFT's share (`nftCompoundedAmountsByTokenId`), since its mint value already contained the earlier compounds. Both removals are the saved coins priced at the current poll, so IL/G does not drift as the pair moves after a compound. `ilFigures` (`src/bot-pnl-il.js`) is the single expression of both figures and is pure — no bot state, no snapshot, no I/O — so the bot tier (`_computeIL`, same file) and the view tier (`src/position-details.js` and `position-details-quick.js`, for unmanaged positions) share it rather than each keeping a copy. That sharing is what makes a position report the same IL/G whether or not the bot manages it: managing one changes nothing on chain, so nothing on screen may move. Pinned by `test/il-managed-unmanaged-parity.test.js`. `computeHodlIL` itself is unchanged. In the lifetime figure, the pool-scoped wallet residual (coins the LP gave back to the wallet during prior rebalances and is about to fold back in on the next one) is credited to the LP-side — without this, IL/G overstates losses on low-liquidity pairs whose rebalance swaps leave material residuals (invisible on high-liquidity pairs whose swaps absorb everything cleanly). Per the user's "simple a vs b" mandate, the initial-mint residual is NOT subtracted from the credit; accepted edge case is that a freshly minted LP whose only residual IS the initial mint leftover will show +$X of IL/G until the first rebalance folds that leftover into the position. The dashboard surfaces the initial residual as a separate Lifetime panel line item. Negative = loss vs holding. Two separate IL values: `snap.totalIL` (current position, from `hodl-baseline.js`) and `snap.lifetimeIL` (from first epoch's deposited amounts). HODL baseline stores actual deposited amounts (`hodlAmount0`, `hodlAmount1`) plus historical prices only for initial deposit auto-detection. Persisted as the `hodlBaseline` record in `app-data/position-records.json`.

**Deposit count:** coins the owner sends to the wallet are money put in, and `src/deposit-count.js` records them as they arrive, so no figure reads them as the position's gain: every poll credits the wallet's coins to the position in the Lifetime figures, and the Lifetime scan counts a deposit only once a rebalance has minted it. The Current IL/G and the Guard count no coin in the wallet, so they need no count. It reads the wallet's transfers from the block after the last one counted to the chain's head, by the Lifetime scan's own rules (`depositsInWindow`, `src/wallet-deposits.js`), starting after the latest of the last read (`countedThrough`), the newest mint the Lifetime results cover (`lastBlock`) and the current NFT's mint. It runs as the first step of every rebalance and compound, and when a poll sees the wallet's coins rise, or is the first after a move's count, since the move takes coins a later deposit could hide behind (`countDepositsOnRise`). A move's count is the record: its deposits go into the pool's Lifetime results in the epoch cache at their own blocks, each naming its transaction, and are priced into Total Lifetime Deposit; the Lifetime scan's next window leaves those transactions out, so each counts once, and a scan writing while a count landed keeps it (`withLaterCounts`). A poll's count is held in memory (`_depositOverlay`) until the next move's count reads the same blocks and records its own answer. The Lifetime figures add the poll's (`src/counted-deposits.js`). A count never stops a move. Full detail in docs/engineering.md § "Deposit Count".

**Wallet residual tracking:** `src/residual-tracker.js` tracks per-pool token residuals (collected − minted deltas across rebalances). Residuals are capped to actual wallet `balanceOf` when computing USD value, so sold/transferred tokens aren't over-counted. Users account for sold tokens via "Edit Realized Gains". Persisted as the `residuals` record in `app-data/position-records.json`.

**Throttle/doubling:** 3 rebalances within 4× minInterval switch on doubling mode (10m → 20m → 40m → 80m…), which clears after a quiet spell of 4× currentWait or at the midnight UTC reset. All timing resets are UTC. The three numbers are `throttleDoubling` in `bot-config-defaults.json`, override applied, ranges in `setting-bounds.json`; `src/throttle.js` enforces them, and the dashboard's trigger-window label and help get the same resolved numbers.

**Epoch cache (pool-keyed P&L):** `src/epoch-cache.js` stores P&L epochs in `app-data/scan-cache/pnl-epochs-cache.json`, keyed by **pool identity** (`blockchain.contract.wallet.token0.token1.fee`) instead of by tokenId. This means P&L history survives rebalances (which mint new tokenIds) without migration. On bot loop start, `getCachedEpochs()` restores the tracker state; `setCachedEpochs()` persists after each update via `_persistEpochCache()` in `server-positions.js`. Supports both full tracker state `{ closedEpochs, liveEpoch }` and legacy array format.

**Cache scoping pattern:** All disk caches use a consistent scoping pattern for multi-chain/multi-wallet isolation:

- **Event cache:** `event-cache-{cacheTag}-{contract}-{wallet}-{token0}-{token1}-{fee}.json`
- **LP position cache:** `lp-position-cache-{cacheTag}-{contract}-{wallet}.json`
- **Epoch cache:** keyed by `blockchain.contract.wallet.token0.token1.fee` within a single JSON file; `src/epoch-cache.js` supplies the active chain's name itself
- **Liquidity-pair details cache:** `liquidity-pair-details-cache.json` — single file keyed by `{cacheTag}-{factory}-{wallet}-{token0}-{token1}-{fee}` (byte-identical suffix to the event-cache filename, built by the shared `liquidityPairScopeKey()` helper in `src/cache-store.js`). Stores `initialResidualData` per scope: the wallet's token0/token1 balances + USD prices captured at the end of `firstMintBlock` (post-mint state — what was left over after the very first IncreaseLiquidity TX consumed its inputs). Subtracted from the live Wallet Residual figure so Lifetime Net P&L reflects only residuals produced by subsequent rebalances/compounds, not the unavoidable leftover from the initial mint.

The event, LP-position and liquidity-pair caches name a chain by its `cacheTag` in chains.json (`pulse` on PulseChain), read through `chainCacheTag()` in `src/cache-store.js`: every chain declares its own, no two may share one, and there is no fallback. Those three abbreviate addresses to their first 6–8 hex characters to keep names manageable. The epoch cache is the exception on both counts: its keys carry the chain's chains.json key and full lowercase addresses.

**Every other cache of chain data leads its keys with the chain.** `cacheKey(chain, ...parts)` in `src/cache-store.js` is the canonical form — the chain's chains.json key, then what identifies the entry, dash-joined and lower-cased — because a token or pool can sit at one address on two chains, and PulseChain's copy of Ethereum's state means many do. It keys token symbols (`chain-token`), pool creation blocks (`chain-factory-pool`), NFT mint dates (`chain-positionManager-tokenId`), closed-position decimals, current prices and GeckoTerminal's pool orientation (`chain-pool`) and best pool (`chain-token-address`); the pool scanner's recent-scan reuse uses the canonical pool key from `src/pool-key.js`. A wallet scan reads and writes the LP-position cache of the contract it scanned. The browser keeps the position list, the managed set and the last position viewed per chain (`9mm_position_store_<chain>` and so on), since it outlives a server restarted on another chain at the same address. `public/dashboard-chain-storage.js` reads and writes them, touching none until the server names the chain: the page's buttons work before then, and a key built from an unknown chain would end in `_null`.

**Position switch consolidation:** All position activation paths (user selection, deep link, bot sync) flow through a single `_activateCore(idx, opts)` helper in `dashboard-positions.js`. This ensures consistent state cleanup on every switch: closes every dialog that belongs to the position leaving the screen, each as its own Cancel or Close does and before the switch, so a Save can never land on the next position (`closePositionDialogs`, `public/dashboard-position-dialogs.js`; the user's decision, 2026-10-18), while the server's alerts, each naming its own position and shown once, stay open (`_alertModal`, `public/dashboard-alerts.js`), exits closed-position view, clears localStorage rebalance event cache (`resetHistoryFlag()`), resets config sync flag (`_configSynced`), updates the position store, applies config, syncs the URL, and fires an immediate status poll (`pollNow()`) so the new position's server data appears instantly without waiting for the 3-second interval. `resetHistoryFlag()` in `dashboard-data.js` is a standalone function that can be called independently without resetting all polling state.

**Stale figures after a switch:** from the moment a position comes on screen until the server has answered about it, the figures on screen may still be the previous position's. `public/dashboard-stale-data.js` is the single source of truth. It records the key of the position the last fresh answer was about (the status poll for an open managed position, the details request for an unmanaged one, the history request for a closed one, an error answer included), and the figures are stale whenever the position on screen has another key, so every path that changes the position on screen makes them stale with no step of its own. The dashboard holds one status answer at a time, so one read for another position forgets the fresh one. A watch reads the flag every `staleDataCheckIntervalMs` (50 ms as shipped, beside `dashboardPollIntervalMs`) and, while it is set, puts `data-position-data-stale` on the body: the stylesheet shows a plain dash for every `data-position-figure`, hides each `data-position-graphic` (the range and composition bars) and swaps each history table's rows for a row of dashes, and the watch makes every part of the page inert except the disclaimer and the wallet unlock. `_activateCore` empties the Bot Settings boxes holding the position's settings (Approval Multiple, the install's, keeps its value); their dash placeholder shows until the new position's answer fills them. With no answer the figures stay stale, and each status answer asks again for an unmanaged position's details or a closed one's history; an unanswered details request goes no further, so it is asked again at the poll's pace rather than in a loop.

**Wallet validation:** 3 states — `invalid` (red), `valid-known` (green, import immediately), `valid-new` (amber, confirmation required). On-chain activity detection via `getTransactionCount`.

**FOUC prevention:** Range status banner is hidden on page load and only shown after real price data arrives from the bot. Prevents false "OUT OF RANGE" flash on refresh.

**Closed position viewing:** Users can browse closed positions (liquidity=0) in the Position Browser. `dashboard-closed-pos.js` manages a "history viewing mode" that fetches historical P&L data via `GET /api/position/:tokenId/history` (backed by `src/position-history.js`) and displays it without disrupting the bot's active position. An amber banner shows "Viewing closed position NFT #..." with a "Return to Active Position" button. KPI updates are paused in closed-view mode (`isViewingClosedPos()` gate in poll handler).

**User Manual:** the "User Manual" link in the header opens `public/help-and-user-manual.html`, which explains the single-position-per-pool model, fund tracking/recycling, range width, volatility doubling, gas cost protection, closed positions, and troubleshooting (rebalance timing).

**Sync indicator:** "Done Syncing" / "Syncing..." badge at the bottom of the Cumulative P&L card tracks the 5-year event scanner progress.

**Client-side URL routing:** Navigo (~5KB) provides pushState-based routing. URLs follow the pattern `/pulsechain/:walletAddress/:nftContractAddress/:tokenId` for bookmarkable/shareable deep links. The first segment is the blockchain name (`pulsechain`). Server has a SPA catch-all: extensionless GET paths serve `index.html`; paths with file extensions that don't match a real file return 404. Deep-link resolution: if the wallet matches the loaded wallet, the router looks up the tokenId in posStore and activates it via `activateByTokenId()` (display-only — does NOT trigger server position switch). If not found, it scans the wallet and looks once more when that scan finishes (the server answers a scan already running with its result, so a concurrent scan is waited for, not raced). Pending route targets are stored when the wallet isn't loaded yet and resolved after wallet import/restore. URL updates use `router.navigate()` with `callHandler: false` to avoid re-triggering route handlers. `syncRouteToState()` updates the URL when the bot's active position changes (e.g. after rebalance), allowing the update when the URL's tokenId differs from the active position's tokenId.

**Dead code detection:** `knip`, configured by `knip.json` and **gated on unused FILES only** — `npm run knip:files` runs inside `npm run lint` and `npm run check`, so a file nothing reaches fails the build. The config exists to make that answer trustworthy: knip cannot see that `scripts/`, `util/` and `test/` hold entry points invoked from a shell rather than imported, so without declaring them it called working CLI tools dead and then called the dependencies they alone used unused. Declaring them took unused files from nine to zero and unused devDependencies from nine to six. Unused **exports** are deliberately NOT gated: `public/dashboard-*.js` is reached through HTML `<script>` tags knip cannot trace, and `src/` and `util/` export their internals on purpose so tests and other tools can compose them — an export nothing imports yet is a seam, not a defect. Run bare `npm run knip` to see those, as information.

**Idle-driven price-lookup pause:** Token-price endpoints are quota-limited, so `fetchTokenPriceUsd` and `fetchDustUnitPriceUsd` are gated at the public API of `src/price-fetcher.js` (single chokepoint shared by bot + server tiers). Four pause sources, each able to pause on its own: (1) **server-side idle tracker** (`src/server-idle-tracker.js`, wired by `src/server-pause.js`) flips paused after 15 min of zero `/api/*` traffic; the tracker uses a self-rescheduling `setTimeout` chain so a slow `_check` can never overlap with the next tick and a backlog can never accumulate; (2) **browser-side idle** (`public/dashboard-idle.js`) posts `/api/pause-price-lookups` after 15 min of no input and `/api/unpause-price-lookups` on the next throttled (500 ms) activity event (focus/click/key/touch/pointer); the no-input timer's callback closes over its own `armedAt` and self-cancels if it fires more than `15 min + 2 s` after arming, so a long-deferred callback flushed by Chrome after a hidden-tab interval can't produce a spurious pause; (3) **move-scoped override** (`withFreshPricesAllowed` in `src/price-fetcher-gate.js`) is a counter that bypasses both the pause flag and cache TTL for the duration of every auto- or manual-triggered rebalance/compound, restoring prior state on success or throw; (4) **headless `bot.js` startup** calls `pausePriceLookups()` by default — operators opt out with `--start-with-price-lookups-unpaused`. `/api/*` traffic resets the server idle countdown but never auto-unpauses (would fight the browser-issued pause). Two configurable global keys: `priceCacheTtlMs` (default 120 000) and `dustUnitPriceCacheMultiplier` (default 30); dust-unit-price TTL is `priceCacheTtlMs × multiplier` with a runtime integer-multiple assertion. Critical rebalance/compound logic lives in the bot tier; server tier hosts only view-only endpoints (`server-routes.js`, `position-history.js`, `position-details.js`); both share `src/price-fetcher.js`. The browser-side flag (`isBrowserPaused()` in `public/dashboard-idle.js`) is also the gate for `playSound()` in `public/dashboard-sounds.js`: polling-driven rebalance/compound jingles are suppressed while the dashboard is idle, so a user returning to a long-untouched tab is not greeted with a backlog of event sounds (`playSoundAlways()` for Easter Egg / title tune is unaffected; the move-scope bypass never touches the browser flag). See `docs/architecture.md` "Idle-Driven Price-Lookup Pause" for the full state machine.

**Balanced-band Telegram notification:** An optional alert, once per FALSE→TRUE entry into the USD-balanced band (token0 USD value / total within `positionBalancedBandPct` of 50/50, ±2.5 points as shipped), with a `positionBalancedCooldownMs` cooldown (30 minutes as shipped) against oscillation; both are in `bot-config-defaults.json`, ranges in `setting-bounds.json`. Pure logic is in `src/telegram-notifications/balanced-notifier.js`; its per-position state lives, unpersisted, on the bot-state object from `src/server-positions.js`. It runs in `updatePnlAndStats` (`src/bot-pnl-updater.js`) after the snapshot, through `notify()` as the `positionBalanced` event (default OFF). When enabled, its fresh-price probe bypasses the idle-driven price-lookup pause (`withFreshPricesAllowed`) once per `pricePauseExceptionPollWindowMultiple` polls (default 10: 50 min at the default 300 s poll). The alert's header quotes the band, and the live figure reaches the dashboard via `GET /api/telegram/config`, keeping the checkbox label's percent in sync. `public/dashboard-telegram.js` shows the cost and cadence beside the checkbox.

**Rebalance diagnostic logs:** Step-by-step console logs trace the entire rebalance pipeline: Steps 1 (getPoolState), 2 (ownerOf), 3 (readLiquidity), 3a (removeLiquidity), 6 (swap), 7a (allowance), 7b (mint TX submit), 7c (mint TX confirm). Each TX confirmation logs `gasUsed`, `gasPrice`, and `blockNumber`. Every `getFeeData()` call logs the returned `gasPrice`, `maxFeePerGas`, and `maxPriorityFeePerGas` values. Speed-up replacements log original/current/bumped gas and the replacement TX hash. Position detection, bot state changes, and `activePositionId` transitions are also logged. These logs are permanent — not removed after debugging.

## Lint Rules

**ESLint** (`eslint:recommended` + custom):

- `complexity ≤ 17` (error)
- `max-lines ≤ 500` skipBlankLines skipComments (error)
- `eqeqeq always` + `no-var` + `prefer-const` + `strict global`
- `no-unused-vars` — `vars: 'all'` for src/test, `vars: 'local'` for dashboard
- `no-restricted-syntax` — disallows `window.*` assignments
- `9mm/no-separate-contract-calls` — custom rule requiring atomic EVM method pairs (e.g. `decreaseLiquidity` + `collect`) to use `multicall`, not separate awaits. Configurable via `pairs` option. Source: `eslint-rules/no-separate-contract-calls.js`
- `n/no-missing-import` (dashboard ES modules) and `n/no-missing-require` (Node CommonJS) — fail lint when an `import`/`require` path can't be resolved. Closes the gap where a renamed dashboard module's stale import passed lint+tests+CI green and only blew up at esbuild time. Wiring is guarded by `test/eslint-config-import-resolution.test.js`.
- `--max-warnings 0` treats warnings as errors
- No `eslint-disable` directives

**stylelint** (`stylelint-config-standard`, `.stylelintrc.json`):

- Standard CSS rules with overrides for: `selector-class-pattern` (allows `9mm-pos-mgr-` prefix), `custom-property-pattern`, `no-descending-specificity`
- `9mm/no-linebreak-after-escape` — custom rule rejecting a CSS character escape stranded at the end of a line. A wrapped `.\39` silently truncates the class name to `9` and turns the rest into a descendant type selector, so the rule stops applying with every gate still green. Fix by switching that selector to the six-digit `.\000039mm-pos-mgr-…` form. Source: `stylelint-rules/no-linebreak-after-escape.js`; background in docs/engineering.md § "CSS Class-Name Escapes"
- Runs on `public/*.css`

## Constraints to Maintain

- **NEVER put cache data in a configuration file.** Files under `app-config/` hold only what the operator chooses. What is read from the blockchain or a price service, or worked out from it, goes in `app-data/scan-cache/` (its path from `scanCachePath`, `src/scan-cache-dir.js`); what the bot records about a position goes in `app-data/position-records.json` (`RECORD_POSITION_KEYS`); `tmp/` holds nothing worth keeping. `test/data-homes.test.js` fails the build otherwise.
- **Only a program's entry point runs anything when it is loaded**: the file the program starts from (`server.js`, `bot.js`, a script, a `util/` tool's `index.js`, `public/dashboard-init.js`). Every other file's top level only declares: imports, constants, functions, classes, exports. A value a library needs from the settings is read by a function the entry point calls (e.g. `readPriceCacheSettings`, `src/price-fetcher-gate.js`). Code that predates this rule is changed one case at a time, when asked.
- Every `src/` and `public/dashboard-*.js` file ≤ 500 non-comment lines of code
- No function with cyclomatic complexity > 17
- No `eslint-disable` directives for main lint rules; no `stylelint-disable` directives. Security lint rules (`9mm/no-number-from-bigint`, `9mm/no-secret-logging`) may use per-line `eslint-disable-next-line` with a documented `-- Safe: <reason>` comment
- Never exclude entire files from any lint pass — use per-line directives for specific exceptions
- No `window.*` property assignments
- Full JSDoc on every file and exported function
- All new code covered by tests in `test/`
- `npm run check` must pass clean before any commit
- EVM addresses use EIP-55 checksummed capitalization
- All dollar amounts denominated in USD
- V3 positions only — reject V2 with helpful error message
